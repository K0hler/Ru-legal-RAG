# ARLC 2026: разбор конкурсных Legal RAG и выводы для нашего проекта

**Дата сводки:** 23 сентября 2026 года  
**Назначение:** собрать в одном месте разбор статьи Тагира, комментариев к ней, открытых материалов призёров Agentic Legal RAG Challenge 2026 и практические выводы для нашего Legal RAG.

## 1. Как читать этот документ

Здесь разделены три вида информации:

- **подтверждённый факт** — официальный лидерборд, публичный репозиторий или непосредственно описанная архитектура;
- **утверждение автора решения** — опубликованный автором результат эксперимента, который мы не воспроизводили на своём корпусе;
- **вывод для проекта** — наша инженерная рекомендация, которую ещё нужно проверить на русском юридическом gold set.

Конкурс решал узкую задачу: ответить на вопросы по корпусу DIFC и указать точные физические страницы PDF. Наш проект решает более широкую задачу: найти юридически применимую норму в правильной редакции и дать проверяемую ссылку. Поэтому конкурсные решения нельзя переносить буквально.

## 2. Короткий итог

Самые сильные повторяющиеся идеи в рассмотренных работах:

1. Качество извлечения PDF и OCR является частью retrieval, а не технической мелочью.
2. Каждый поисковый фрагмент должен знать, из какого документа, дела, закона и структурного элемента он взят.
3. Точные реквизиты — номер дела, закона или статьи — надо извлекать и использовать до общего семантического поиска.
4. Поиск сначала ограничивают подходящими документами, а затем ищут доказательство внутри них; параллельно полезно сохранять более широкий резервный поиск.
5. Для вопросов по нескольким документам надо гарантировать представительство каждого документа в контексте.
6. Ответ и доказательство отбираются отдельно: найденный фрагмент ещё не обязательно является хорошей цитатой.
7. Улучшения оцениваются по стадиям: разбор документа, маршрутизация, retrieval, отбор доказательств, цитирование и итоговый ответ.
8. Простая измеримая система часто надёжнее большой автономной агентной конструкции.

Главный вывод о чанках: **страница была основной единицей конкурса из-за метрики `(doc_id, page_number)`, а не потому, что страница является лучшей смысловой единицей юридического текста**. Для нашего проекта канонической единицей должна оставаться норма — статья, часть, пункт или подпункт, — а страница и смещения должны храниться как координаты доказательства.

## 3. Что представлял собой конкурс

[Agentic Legal RAG Challenge 2026](https://agentic-challenge.ai/leaderboard) использовал корпус документов DIFC: судебные решения, законы, регламенты, приказы и консультационные документы.

Задача системы:

1. найти нужный документ;
2. найти нужные страницы;
3. дать ответ в строго заданном формате;
4. вернуть точные ссылки на страницы;
5. сделать это с приемлемой задержкой.

Поддерживались типы ответа:

| Тип | Требуемый результат |
|---|---|
| `number` | Число |
| `boolean` | `true` или `false` |
| `name` | Одно имя или название |
| `names` | Массив имён |
| `date` | Дата в установленном формате |
| `free_text` | Короткий свободный ответ |
| `null` | Информации нет в корпусе |

В статье Тагира формула оценки приведена в виде:

```text
Total = (0.7 × S_det + 0.3 × S_asst) × G × T × F
```

Где:

- `S_det` — точность типизированных ответов;
- `S_asst` — оценка свободного ответа LLM-судьёй;
- `G` — grounding по правильным страницам, рассчитанный через F-beta с `β = 2.5`;
- `T` — валидность телеметрии;
- `F` — коэффициент задержки до первого токена.

Ключевая особенность: grounding являлся **множителем**. Хороший текстовый ответ с неправильными страницами всё равно получал низкий итоговый балл. Это заставляло участников оптимизировать не только ответ, но и его проверяемость.

## 4. Решение Тагира: подробный разбор

Источник: [«Как я за 5 дней построил Legal RAG...»](https://habr.com/ru/articles/1014758/).

### 4.1. Общая архитектура

В решении использовались:

- извлечение текста из PDF;
- OCR как запасной путь для страниц без текста;
- индекс по физическим страницам;
- BM25 для точных совпадений;
- embeddings для семантического поиска;
- Reciprocal Rank Fusion для объединения двух выдач;
- отдельный индекс маршрутизации по делам и законам;
- cross-encoder reranking;
- приоритетные страницы, которые reranker не мог удалить;
- специальные быстрые пути для некоторых типов вопросов;
- сокращение нерелевантных частей страницы перед передачей LLM;
- структурированный разбор ссылок из ответа модели;
- постпроверка части числовых и именных ответов по исходному тексту;
- отдельная логика определения страниц, которые действительно следует цитировать.

Упрощённо поток выглядел так:

```text
PDF
  → извлечение текста / OCR
  → постраничный индекс
  → BM25 + embeddings
  → RRF
  → маршрутизация по реквизитам
  → reranking и защищённые страницы
  → сокращённый контекст
  → LLM или быстрый детерминированный путь
  → проверка ответа
  → выбор страниц для grounding
```

### 4.2. Почему использовались страницы, а не смысловые разделы

Grounding конкурса сравнивал пары `(doc_id, page_number)`. Если бы чанк пересекал границу страниц, возникал бы вопрос, к какой странице его относить. Поэтому автор сделал одну физическую страницу одной индексируемой записью.

Это решение было рациональным для конкурса, потому что:

- единица индекса совпадала с единицей оценки;
- ссылка на источник получалась напрямую;
- не требовалось восстанавливать страницу из произвольного чанка;
- было проще контролировать число страниц в финальной цитате.

Недостатки такого решения:

- статья может начинаться на одной странице и продолжаться на другой;
- одна страница может содержать несколько разных статей;
- заголовок и юридическое условие могут оказаться разделены;
- длинная страница раздувает контекст;
- одинаковые по стилю страницы разных документов конкурируют друг с другом;
- физическая верстка PDF начинает определять логику поиска.

В комментариях автор прямо подтвердил, что для production-системы с другой метрикой более мелкое chunking-разбиение разумно. Он также признал, что при росте корпуса требовалась более сильная предварительная классификация документов.

### 4.3. Что у автора действительно помогло на warmup

По собственным экспериментам автора:

| Приём | Наблюдавшийся эффект | Практический смысл |
|---|---:|---|
| Исправление формата `doc_id` | Grounding вырос примерно с 0.05 до 0.55 | Сначала проверять контракт данных, потом менять модели |
| BM25 + embeddings | Улучшение grounding на warmup | Точные реквизиты и перефразировки требуют разных сигналов |
| Article index | Улучшение выбора страниц | Прямое попадание в статью надёжнее случайного упоминания |
| Smart continuation | Улучшение grounding | Соседняя страница добавляется только при продолжении той же статьи |
| Ограничение числа цитируемых страниц | Меньше шума | Лишняя страница ухудшает precision |
| Детерминированные быстрые пути | Меньше задержка и стоимость | Простые факты не всегда требуют LLM |
| Post-LLM проверка чисел и имён | Меньше очевидных галлюцинаций | Результат модели можно сопоставить с источником |
| Context distillation | Экономия токенов | В LLM передаётся полезная часть длинной страницы |

Лучший warmup-вариант автора достиг `0.791`, в том числе `G = 0.862`.

### 4.4. Что не сработало

Автор зафиксировал несколько регрессий:

- автоматическое добавление соседних страниц: соседняя страница часто уже относилась к другой статье;
- добавление большего числа страниц ради recall: шум снижал grounding;
- предметные подстановки после ответа LLM: эвристика неверно трактовала пограничные роли;
- изменение настроенного free-text-промта: качество на оценке снизилось;
- множество изменений одной пачкой: невозможно понять, какой компонент дал эффект;
- слишком широкие регулярные выражения: номер закона ошибочно принимался за искомое число;
- подстановка цитаты в вопросах без ответа: когда gold ожидал пустой список страниц, такая цитата ухудшала precision.

Особенно важно: некоторые удачные конкурсные правила были подогнаны под конкретный evaluation protocol. Их нельзя считать универсальными правилами юридического RAG.

### 4.5. Почему решение просело на финальном корпусе

При переходе примерно от 30 к 303 документам итоговый результат упал с `0.791` до `0.457`; официальный лидерборд показывает итог `0.457134`.

Автор выделил следующие причины:

1. **Retrieval dilution.** Большой документ на сотни страниц забивал выдачу общей юридической лексикой.
2. **Неоднозначность документов.** Несколько consultation papers имели одинаковые номера, но разные годы и темы.
3. **Слабая маршрутизация.** Она хорошо работала для номеров дел, но хуже — для законов и консультационных документов.
4. **Ошибки регулярных выражений.** Правило для номера закона срабатывало на вопросы о штрафах и суммах.
5. **Case-number leakage.** Модель принимала число внутри номера дела за ответ на количественный вопрос.
6. **Пропущенный OCR.** Два сканированных документа оказались фактически невидимы поиску.
7. **Проблема кеша.** Warmup-данные временно подменили финальный корпус.
8. **Недостаток локального gold set.** Эксперименты зависели от ограниченного числа публичных отправок.

Практический урок автора: сначала выбрать документ по заголовку, типу и реквизитам, затем искать страницы внутри него; отдельно провести синтетический scaling test с шумовыми документами.

### 4.6. Что добавили комментарии

Из ответов автора в комментариях следует:

- один корпус использовался для всех вопросов соответствующей фазы;
- сами вопросы становились известны при запуске фазы, но заранее были известны только форматы ответа и общие категории;
- классификация документов частично существовала внутри retrieval;
- для большого корпуса её следовало формализовать сильнее;
- page-level был продиктован метрикой;
- для production-системы допустимо и разумно использовать более мелкие чанки с overlap;
- значительная часть итераций исправляла системные ошибки, но некоторые улучшения действительно были специфичны для конкурса.

## 5. Gless AI: второе место

Источники: [полный технический разбор](https://www.linkedin.com/pulse/how-we-built-legal-rag-system-placed-2nd-out-350-gleb-drozdov-qesje/) и [русская версия](https://glebdrozdov.pro/blog/legal-rag-hakaton).

### 5.1. Подготовка документов

Команда сравнила несколько PDF-парсеров на своих данных. По утверждению авторов:

- Docling создавал ложную иерархию из нумерованных статей, раздувал таблицы и иногда терял сведения из многострочных блоков;
- PyMuPDF сохранял текст, но терял структуру;
- OpenDataLoader оказался лучшим из проверенных вариантов на конкурсном корпусе;
- страницы-изображения обрабатывались vision OCR через Gemini 2.5 Flash.

Это не доказывает универсальное превосходство одного парсера. Важно другое: парсер выбирался экспериментом на реальных документах и конкретных полях, а не по README.

### 5.2. Метаданные как часть поискового текста

Для каждого документа извлекались:

- номер дела;
- заголовок;
- номер закона;
- другие реквизиты документа.

Метаданные сохранялись в payload Qdrant и одновременно добавлялись в начало текста перед построением embedding. Например, страница судебного решения получала заголовок с номером дела и названием сторон.

Простыми словами: страница переставала быть безымянным абзацем. Вектор содержал не только содержание страницы, но и её документную идентичность.

Использовались embeddings семейства Voyage-4: документы индексировались более тяжёлой моделью, запросы — более лёгкой совместимой моделью. Это авторское техническое решение, которое следует сравнивать с локальными русскоязычными моделями, а не копировать автоматически.

### 5.3. Обработка запроса

Gless AI отказалась от LLM query rewriting, HyDE и LLM-маршрутизации: на warmup они не улучшили результат, но добавляли, по словам команды, примерно 500–800 мс.

Вместо этого использовались:

- регулярные выражения для форматов номеров дел;
- нормализация найденных реквизитов;
- отдельный фильтрованный поиск для каждого упомянутого дела;
- общий нефильтрованный поиск как запасной путь;
- отдельный reranking каждого пула;
- гарантированное включение нескольких лучших результатов каждого дела в финальный контекст.

Это решало проблему cross-document вопросов: общий embedding одного вопроса мог быть чуть ближе к одному делу и полностью вытеснить второе из top-k.

### 5.4. Генерация ответа

Команда использовала структурированный JSON с последовательностью:

```text
reasoning → answer → used_pages
```

Идентификаторы документов перед передачей модели заменялись короткими псевдонимами `D1`, `D2` и так далее, после ответа восстанавливались. Это уменьшало промт и упрощало модели отслеживание ссылок.

По заявлению команды, итоговый результат составил около `76.7`, а медианная задержка — `1.97 с`. Место и нормализованный балл подтверждаются официальным лидербордом; внутренние измерения задержки и абляций являются данными авторов.

### 5.5. Что Gless AI попробовала и отбросила

По результатам их warmup:

- BM25 + RRF не дали улучшения поверх Voyage-4 с добавленными метаданными;
- query rewriting и decomposition не улучшили результат;
- HyDE не окупил дополнительную задержку;
- контекстная embedding-модель сделала страницы одного документа слишком похожими;
- более медленная генеративная модель не дала нужного выигрыша;
- автоматически построенный финальный golden dataset оказался хуже основной системы на выборочной проверке.

Это особенно полезно как предупреждение: популярная технология не обязана помогать, если её сигнал уже воспроизводится другим компонентом.

## 6. CPBD: третье место и открытый репозиторий

Источники: [репозиторий](https://github.com/azamat1ch/difc-legal-rag), [описание решения](https://github.com/azamat1ch/difc-legal-rag/blob/main/docs/solution.md) и [описание gold labeling](https://github.com/azamat1ch/difc-legal-rag/blob/main/docs/gold-labeling.md).

### 6.1. Основная ставка: сначала evaluation

Автор сначала построил локальный контур оценки:

1. отдельный labeler создавал эталонный ответ;
2. verifier пытался найти ошибку в ответе и страницах;
3. дополнительный аудит проверял согласованность ответа и grounding;
4. отдельно измерялись retrieval, отбор страниц, citations и итоговый ответ;
5. изменения сохранялись только после измеренного улучшения.

Это одна из самых переносимых идей всей работы. Однако автоматически созданный gold остаётся proxy-набором: для юридически значимого русского корпуса критические примеры должен проверять человек.

### 6.2. Офлайн-конвейер

Опубликованное решение включало:

- разбор PDF через Marker/Datalab;
- нормализацию страниц, блоков, разделов и метаданных;
- извлечение юридических сущностей, структуры и ссылок на статьи через Isaacus Kanon 2;
- создание кратких page summaries через Gemini Flash;
- SQLite FTS5;
- sqlite-vec;
- отдельные индексы статей и названий законов;
- section-level и page-level представления.

По описанию автора, финальный индекс содержал 939 sections и 4 056 pages для 300 PDF. Эти числа относятся к конкурсному корпусу и не являются характеристикой нашего LAW_Data.

### 6.3. Онлайн-конвейер

Упрощённая схема:

```text
Вопрос
  → SearchPlanner
  → hybrid retrieval
  → специальные rescue/injection rules
  → адаптивный top-k
  → PageSelector
  → schema-guided answer
  → проверенная строка результата
```

Planner и построение embedding запроса запускались параллельно. Онлайн-путь использовал три LLM-вызова: планировщик, отборщик страниц и генератор ответа.

### 6.4. Пять источников кандидатов

Результаты объединялись RRF из:

1. FTS5 по тексту страницы, псевдонимам, summaries, сущностям и ссылкам на статьи;
2. section-level dense search;
3. page-level dense search;
4. прямого article-reference lookup;
5. document-filtered dense search по документам, выбранным planner.

По утверждению автора, document-filtered dense search дал самый заметный выигрыш retrieval. Один глобальный top-k был заменён разными бюджетами для разных маршрутов и типов ответа.

### 6.5. Отбор доказательств

Answer model возвращал:

- анализ вопроса;
- оценку доказательств;
- решение об answerability;
- итоговый ответ;
- метку `CITE` или `SKIP` для каждого отрывка.

В итоговые ссылки попадали только фрагменты с `CITE`. Это полезное разделение: retrieval собирает кандидатов с запасом, а citation selection оставляет только доказательства.

### 6.6. Что не сработало у CPBD

Автор отдельно указал:

- cross-encoder иногда поднимал keyword-heavy титульные страницы;
- section-level и enriched-chunk retrieval не превзошли page-level в конкурсной метрике;
- параллельный отбор внутри каждого документа был дорогим и ухудшал глобальное сравнение;
- детерминированное извлечение становилось хрупким на редких случаях;
- полностью автономная оптимизация уходила в переобученные эвристики без человеческой проверки.

Последний вывод особенно важен: CPBD называет систему не «гигантским агентом», а измеримым конвейером, где LLM используется лишь в нескольких точках, в которых от неё был измеренный эффект.

### 6.7. Ограничения использования открытого кода

На момент проведённой проверки:

- в репозитории CPBD не была обнаружена лицензия;
- финальные конкурсные PDF и полные финальные labels не опубликованы;
- полный запуск зависит от внешних API Datalab, Isaacus, Cerebras и Gemini;
- поэтому архитектуру можно изучать и независимо воспроизводить, но нельзя автоматически считать код разрешённым для копирования в наш проект.

[neonsecret/ai-challenge-legal](https://github.com/neonsecret/ai-challenge-legal) — архивный публичный проект участника, не идентифицированный как решение одной из трёх призовых команд. Автор сообщал результат ниже призовой тройки и добавлял часть улучшений уже после конкурса.

## 8. Общие удачные паттерны

| Общий паттерн | Как проявился в работах | Объяснение простыми словами | Применение у нас |
|---|---|---|---|
| Контроль извлечения и OCR | Все обрабатывали сканы и проблемы PDF; Gless сравнивала парсеры | Поиск не найдёт то, что парсер потерял | Проверять статьи, пункты, таблицы, приложения и качество OCR до индексации |
| Документная идентичность фрагмента | Routing index у Тагира, metadata injection у Gless, aliases/entities/article indexes у CPBD | Фрагмент должен иметь «паспорт» | Хранить `act_id`, `edition_id`, `provision_id`, реквизиты и координаты оригинала |
| Точные реквизиты как отдельный сигнал | Номера дел, законов и статей использовались до общего поиска | Не надо угадывать известный номер по смыслу | Сначала разбирать название акта, номер, статью, дату и редакцию |
| Поиск внутри выбранного документа | Все три решения ограничивали область поиска хотя бы для части запросов | Сначала выбрать книгу, потом страницу | Маршрут `акт → редакция → положение` плюс широкий резервный поиск |
| Гарантия разнообразия документов | Interleave, per-case pools, diversity rules | Один документ не должен вытеснить второй | Резервировать кандидатов для каждого акта и перекрёстной ссылки |
| Отдельный отбор доказательств | Reranker/priority pages, per-pool rerank, PageSelector/CITE | Найденный фрагмент ещё не обязательно доказывает ответ | Разделить retrieval и claim-level citation selection |
| Разные пути для разных вопросов | Fast paths, regex routing, planner и adaptive top-k | Простая ссылка на статью и сложное сравнение требуют разной работы | Прямой `get_provision` для точных реквизитов, полный retrieval для смысловых вопросов |
| Структурированный выход | Typed answers и JSON использовались всеми | Формат можно валидировать автоматически | Возвращать ответ, evidence handles, статус проверки и основание отказа |
| Корректный отказ | `null` и answerability проверялись отдельно | Лучше признать нехватку доказательств, чем выдумать норму | Тестировать no-answer и false-premise вопросы |
| Поэтапная оценка | CPBD сделал это наиболее полно; остальные опирались на итерации warmup | Нужно знать, на каком этапе потерялась норма | Метрики после routing, retrieval, rerank, citation и answer generation |
| Ограничение сложности и задержки | Fast paths, отказ от лишних LLM-вызовов, параллельные операции | Каждый компонент должен окупать стоимость | Добавлять planner/reranker только после измеренного выигрыша |
| Проверка на масштабе | Финальный провал Тагира показал dilution | Маленький тестовый корпус может скрывать проблемы | Добавлять шумовые документы и длинные акты в scaling test |

## 9. В чём сильные решения расходятся

Именно эти расхождения не позволяют выбрать стек простым голосованием.

| Технология | Наблюдения | Вывод |
|---|---|---|
| BM25 + dense + RRF | Помогли Тагиру и использовались CPBD; Gless не увидела улучшения поверх Voyage-4 с metadata injection | Проверять FTS, dense и hybrid на одном русском gold set |
| LLM query rewriting / decomposition | CPBD сообщил пользу от decomposition; Gless не получила выигрыша и отказалась из-за задержки | Включать только для классов вопросов, где baseline теряет recall |
| LLM routing | CPBD использовал SearchPlanner; Gless предпочла regex и фильтры | Сначала детерминированный разбор реквизитов, затем тест planner на неоднозначных запросах |
| Cross-encoder reranking | Помогал Тагиру; CPBD сообщил, что cross-encoder предпочитал титульные страницы | Нужна собственная оценка и механизм сохранения обязательных кандидатов |
| Page-level retrieval | Хорошо соответствует page-grounding конкурса | Не доказывает превосходство страниц для структурного правового поиска |
| Section-level retrieval | CPBD не получил выигрыша над page-level в конкурсной задаче | Не отвергает нормы/разделы как единицу нашего production-корпуса |
| Детерминированные правила | Сильно ускоряли простые ответы, но ломались на edge cases | Использовать для однозначных реквизитов, покрывать тестами и иметь fallback |
| Обогащение чанков LLM-метаданными | Использовалось Gless и CPBD | Полезная гипотеза, но сначала нужна надёжная каноническая структура и контроль ошибок enrichment |

## 10. Как это соотносится с нашим Legal RAG

Согласно [атласу проекта](PROJECT_ATLAS.md), на срезе 21 сентября 2026 года LAW_Data индексировал плоские фрагменты до 3 500 символов с overlap 350. `LegalEdition`, `LegalProvision`, `SearchChunk`, temporal filtering, hybrid retrieval и citation handles были описаны как **целевая**, а не уже реализованная архитектура.

Целевая модель остаётся обоснованной:

```text
LegalAct
  → LegalEdition
    → LegalProvision
      → одна или несколько SearchChunk
        → координаты страницы и смещения в оригинале
```

Роли сущностей:

- `LegalAct` — идентичность нормативного акта;
- `LegalEdition` — конкретная редакция и период её применимости;
- `LegalProvision` — юридически адресуемая норма;
- `SearchChunk` — поисковая проекция нормы, а не самостоятельный источник права;
- страница и offsets — координаты, по которым пользователь может проверить доказательство.

### Почему это лучше простого page-level для нашего случая

1. Норма не зависит от случайной верстки PDF.
2. Можно выбрать редакцию, действовавшую на дату события.
3. Заголовок, гипотеза, диспозиция и исключения остаются связаны.
4. Поисковый чанк можно менять без изменения канонического источника.
5. Одну длинную норму можно представить несколькими поисковыми проекциями.
6. Ответ всё равно может ссылаться на конкретную страницу и буквальный текст.

Страница остаётся важна, но не как юридическая сущность. Это **evidence coordinate**, а не граница нормы.

## 11. Что переносить в первую очередь

### 11.1. Перенести сейчас

| Приоритет | Компонент | Минимальная реализация | Критерий готовности |
|---:|---|---|---|
| P0 | Контроль разбора PDF | Отчёт по пустым страницам, OCR, структуре и потерянным блокам | Для тестовых документов человек восстанавливает статьи, таблицы и приложения |
| P0 | Канонические реквизиты | `act_id`, `edition_id`, `provision_id`, путь нормы, даты действия, источник | Каждый чанк однозначно ведёт к норме и редакции |
| P0 | Ручной gold set | 30–50 вопросов разных классов с допустимыми нормами и no-answer | Ошибки можно разнести по стадиям |
| P0 | Прямой поиск по реквизитам | `get_provision` по акту, статье и редакции | Точный запрос не зависит от embeddings |
| P1 | Документная маршрутизация | Сначала акт/редакция, затем положение; общий fallback | Большие нерелевантные акты не забивают top-k |
| P1 | Evidence handles | Стабильная ссылка на норму, редакцию, страницу и offsets | Handle проходит детерминированную проверку |
| P1 | Claim-level citation audit | Для каждого утверждения проверяется поддерживающий фрагмент | Неподтверждённое утверждение удаляется или вызывает отказ |
| P1 | Scaling test | Добавить длинные и похожие шумовые документы | Recall не рушится при увеличении корпуса |

### 11.2. Проверить экспериментом

- FTS baseline против dense retrieval;
- FTS + dense через RRF;
- metadata injection в поисковый текст;
- reranker против простого fusion ranking;
- LLM PageSelector против детерминированного отбора;
- query decomposition только для многошаговых вопросов;
- разные top-k для точных, сравнительных и обзорных запросов;
- гарантированное представительство каждого упомянутого акта;
- summary/enrichment как дополнительное поисковое поле;
- сокращение контекста перед генерацией.

Каждый эксперимент должен менять одну переменную и оцениваться на одном и том же наборе вопросов.

### 11.3. Не переносить напрямую

- физическую страницу как каноническую единицу права;
- английские embeddings и rerankers без русского теста;
- конкурсные keyword-эвристики для `null`;
- жёсткие page caps из другой метрики;
- правило «ответ и номер статьи встретились на одной странице — значит доказательство верно»;
- автоматическое добавление соседней страницы;
- сложный planner до появления сильного baseline;
- вывод «BM25 обязателен» или противоположный вывод «BM25 бесполезен»;
- автоматически созданный LLM-gold без человеческой проверки;
- код CPBD без выяснения лицензии;
- полную зависимость от закрытых платных API до сравнения с локальными вариантами.

## 12. Предлагаемый вертикальный эксперимент

Практический первый срез уже согласуется с [целевым конвейером](PIPELINE.md): пять неодинаковых нормативных документов, включая документ с таблицами или приложениями.

### Набор данных

- обычный структурированный НПА;
- документ с частями и подпунктами;
- акт с приложениями и таблицами;
- документ с несколькими редакциями;
- сложный PDF или скан.

### Gold set

Нужны вопросы следующих классов:

- точная статья;
- перефразированный смысл нормы;
- исключение из общего правила;
- отрицание;
- вопрос на дату и редакцию;
- перекрёстная ссылка;
- вопрос по двум актам;
- отсутствующий ответ;
- ложная предпосылка;
- похожие реквизиты разных документов.

### Сравниваемые варианты

```text
A. Текущий плоский FTS baseline
B. LegalProvision + FTS
C. LegalProvision + dense
D. LegalProvision + FTS/dense/RRF
E. Лучший retrieval + reranker или PageSelector
```

### Метрики

- `document recall@k` — найден ли правильный акт;
- `edition accuracy` — выбрана ли правильная редакция;
- `provision recall@k` — найдена ли нужная норма;
- `evidence precision/recall` — насколько чист набор доказательств;
- `citation fidelity` — действительно ли ссылка ведёт к поддерживающему тексту;
- `claim support` — поддерживает ли источник смысл каждого утверждения;
- `correct refusal` — правильно ли система отказывается при отсутствии ответа;
- задержка и стоимость;
- деградация при увеличении корпуса.

## 13. Итоговая рекомендация

Из конкурсных работ следует переносить не конкретную комбинацию моделей, а дисциплину построения системы:

```text
качественный источник
  → каноническая структура и реквизиты
  → узкая маршрутизация с широким fallback
  → retrieval с измеренным запасом
  → отдельный отбор доказательств
  → ответ по доказательствам
  → проверка каждой ссылки
  → ответ или обоснованный отказ
```

Наше структурное разбиение по нормам отменять не нужно. Наоборот, конкурс подтвердил проблему безымянных страниц и плоского поиска по большому корпусу. Из page-level решений стоит взять точную привязку к оригиналу, но не саму страницу как единственную единицу хранения и поиска.

Ближайшая полезная комбинация:

1. **CPBD-style eval-first** — gold set и метрики по стадиям;
2. **Gless-style metadata and scoped retrieval** — реквизиты внутри поискового представления и отдельные пулы для каждого акта;
3. **урок Тагира о масштабе** — document routing и synthetic scaling test до массовой индексации;
4. **наша каноническая модель** — `LegalProvision + LegalEdition` как источник, `SearchChunk` как поисковая проекция, страница как координата доказательства.
