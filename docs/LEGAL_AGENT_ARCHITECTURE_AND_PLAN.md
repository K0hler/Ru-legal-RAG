# Юридический агент: архитектура нормативной базы и план реализации

Статус: рабочий архитектурный документ  
Дата фиксации: 27.08.2026  
Проект: `H:\AI_AGENT\LAW_Data`

## 1. Назначение документа

Этот документ сводит в одно место принятые решения по юридическому агенту, нормативному корпусу, структурному разбору документов, поиску, цитированию и интеграции с агентной LLM.

Документ предназначен для:

- дальнейшего архитектурного анализа;
- декомпозиции реализации;
- фиксации границ системы;
- подготовки технического задания;
- проверки новых решений на соответствие исходным требованиям.

Это не дословная стенограмма обсуждения. Устаревшие и отвергнутые варианты отмечены отдельно.

## 2. Краткий итог

Проекту нужен не готовый RAG-конструктор, а собственный управляемый конвейер обработки нормативной базы.

Целевая схема:

```text
Исходные документы
        ↓
физическое извлечение текста и структуры
        ↓
очистка колонтитулов, переносов и служебного мусора
        ↓
детерминированный юридический структурный парсер
        ↓
каноническое дерево нормативных положений
        ↓
генератор поисковых представлений (chunks)
        ↓
лексический поиск + векторный поиск
        ↓
Reciprocal Rank Fusion (RRF)
        ↓
внешний reranker
        ↓
расширение контекста и формирование проверяемых цитат
        ↓
три узких инструмента агента
```

Основной рекомендуемый стек:

- Docling — физическое извлечение структуры PDF/DOCX;
- собственный `LegalStructureParser` — юридическая иерархия;
- Pydantic — строгие схемы и валидация;
- PostgreSQL — канонические сущности и метаданные;
- pgvector — векторный поиск на первом этапе;
- PostgreSQL FTS — лексический поиск на первом этапе;
- OpenSearch — возможная замена поискового слоя, если понадобится полноценный BM25 и расширенная настройка;
- FastAPI — retrieval API и инструменты агента;
- обычный Python — основная оркестрация;
- Haystack — только необязательная обвязка retrieval-pipeline.

Конкретные LLM, embedding- и rerank-модели не входят в архитектуру корпуса. Они подключаются через адаптеры к внешним API.

| Вопрос | Решение | Статус |

## 4. Контекст продукта

Предполагается юридический продукт, в котором пользователь работает с отдельными проектами или делами.

Продуктовая архитектура:

```text
Frontend
   ↓
Product Backend
   ├── пользователи и организации
   ├── права доступа
   ├── проекты и дела
   ├── структурированное состояние дела
   ├── история изменений
   ├── аудит
   └── пользовательские документы
          ↓
      Agent Runtime
          ↓
      Legal Retrieval API
          ↓
      Нормативный корпус
```

Agent Runtime может быть Hermes Agent или другой совместимый исполнитель. Он не должен быть источником истины для проекта.

Backend хранит:

- факты дела;
- участников;
- хронологию;
- требования;
- расчёты;
- статусы;
- версии создаваемых документов;
- подтверждённые пользователем изменения;
- журнал действий агента.

Мягкая память агента может хранить пользовательские предпочтения, но не заменяет данные проекта и нормативные источники.

## 6. Границы подсистем

Проект следует разделить минимум на четыре независимые области.

### 6.1. `legal_corpus`

Нормативные акты, редакции и положения. Только этот слой может подтверждать нормативно-правовое утверждение.

### 6.2. `case_documents`

Документы конкретного пользовательского дела:

- договоры;
- акты;
- претензии;
- ответы организаций;
- экспертизы;
- фотографии;
- расчёты;
- судебные документы.

Они не смешиваются с нормативной базой в одном неразличимом индексе.

### 6.3. `project_state`

Структурированные данные дела:

- факты;
- участники;
- события;
- суммы;
- заявленные требования;
- процессуальные сроки;
- задачи и статусы.

### 6.4. `agent_memory`

Предпочтения пользователя и рабочий контекст. Не является источником права и не используется для подтверждения юридических выводов.

## 7. Работа с модельными API

Архитектура не должна зависеть от конкретного производителя модели.

### 7.1. Embeddings

Внутренний контракт:

```python
class Embedder:
    def embed_documents(self, texts: list[str]) -> list[list[float]]:
        ...

    def embed_query(self, text: str) -> list[float]:
        ...
```

Основной внешний транспорт — OpenAI-compatible endpoint:

```text
POST /v1/embeddings
```

### 7.2. Reranker

У OpenAI-compatible API нет общепринятого стандартного rerank-контракта. Поэтому проект определяет собственный интерфейс:

```python
class Reranker:
    def rerank(
        self,
        query: str,
        documents: list[str],
        top_n: int,
    ) -> list[float]:
        ...
```

Адаптер может обращаться к:

- `/v1/rerank`;
- Cohere-compatible API;
- Jina-compatible API;
- любому собственному HTTP endpoint.

Остальная система не должна знать тип сервера и название модели.

### 7.3. Chat/agent model

Agent Runtime взаимодействует с LLM через OpenAI-compatible Chat Completions или Responses API. Модель получает только отобранный контекст и типизированные инструменты.

## 8. Конвейер компиляции нормативного корпуса

### 8.1. Этап 1. Регистрация источника

Каждый источник сначала заносится в версионируемый manifest или каталог.

Минимальные поля:

```text
source_id
source_url
downloaded_at
file_name
mime_type
raw_source_hash
publisher
review_status
```

Автоматическое извлечение реквизитов может предлагать значения, но импорт действующего источника не должен завершаться без проверки обязательных полей.

### 8.2. Этап 2. Физическое извлечение

Основной инструмент — Docling.

Результат сохраняется отдельно от следующих стадий:

```text
parsed/<raw_source_hash>.docling.json
```

Нужно сохранять:

- текстовые элементы;
- таблицы;
- страницы;
- координаты;
- порядок чтения;
- предполагаемые заголовки;
- parent/child-связи;
- provenance.

Unstructured используется как резерв для документов, на которых Docling не обеспечивает приемлемое извлечение.

### 8.3. Этап 3. Очистка

Нужны детерминированные правила для удаления или маркировки:

- повторяющихся колонтитулов КонсультантПлюс;
- номеров страниц;
- строки `Документ предоставлен КонсультантПлюс`;
- повторяющихся заголовков акта на каждой странице;
- разрывов слов между страницами;
- служебных блоков выгрузки;
- пустых и почти пустых страниц;
- артефактов OCR.

Удалённый текст должен учитываться в отчёте обработки. Нельзя молча терять содержимое.

### 8.4. Этап 4. Юридический структурный парсер

`LegalStructureParser` строит юридическое дерево документа.

Типы узлов:

```text
document
section
subsection
chapter
article
part
item
subitem
clause
appendix
table
note
amendment_note
```

Парсер должен быть state machine, а не набором независимых регулярных выражений. Интерпретация строки зависит от текущего родителя и типа акта.

Пример дерева:

```text
Постановление Правительства РФ № 354
└── Правила предоставления коммунальных услуг
    └── Раздел IX
        └── пункт 98
            ├── подпункт а
            └── подпункт б
```

### 8.5. Этап 5. Каноническая сериализация

После разбора сохраняется Legal AST:

```text
normalized/<edition_id>.legal.json
```

Это основной проверяемый результат компиляции документа. По нему можно повторно создавать поисковые чанки без повторного OCR и физического разбора PDF.

### 8.6. Этап 6. Генерация поисковых проекций

Chunker принимает Legal AST и создаёт:

```text
chunks/<corpus_version>.jsonl
```

Каждая строка содержит юридически привязанный поисковый фрагмент, а не произвольный отрезок текста.

### 8.7. Этап 7. Индексация

Для каждого chunk создаются:

- лексическое представление;
- embedding-представление;
- фильтруемые метаданные;
- ссылка на канонические положения;
- контекстный заголовок;
- чистый текст цитаты.

### 8.8. Этап 8. Отчёт сборки

Каждая сборка корпуса должна выдавать:

- количество источников;
- количество успешно разобранных редакций;
- количество положений каждого типа;
- количество chunks;
- потерянные или нераспознанные диапазоны текста;
- нарушения схемы;
- дубликаты идентификаторов;
- изменения относительно предыдущей сборки;
- версии парсера, chunker и embedding-модели;
- хеш итогового корпуса.

## 9. Каноническая модель данных

### 9.1. Нормативный акт

```text
legal_act
---------
act_id
title
short_title
act_type
act_number
adoption_date
issuer
jurisdiction
```

`act_id` стабилен между редакциями.

Пример:

```text
ru.gov.pp.354
```

### 9.2. Редакция акта

```text
legal_edition
-------------
edition_id
act_id
edition_date
publication_date
valid_from
valid_to
source_id
source_url
raw_source_hash
normalized_text_hash
parser_version
review_status
```

Пример:

```text
ru.gov.pp.354@2025-12-19
```

`edition_date` и `valid_from` не следует смешивать: изменения могут быть приняты в одну дату, а вступить в силу позднее.

### 9.3. Нормативное положение

```text
legal_provision
---------------
provision_id
edition_id
kind
label
heading
parent_id
order_index
text
page_from
page_to
source_span
valid_from
valid_to
content_hash
```

Период действия может задаваться не только для редакции целиком, но и для отдельного положения.

Пример идентификатора:

```text
ru.gov.pp.354@2025-12-19:rules:section-ix:item-98
```

### 9.4. Поисковый chunk

```text
search_chunk
------------
chunk_id
edition_id
root_provision_id
included_provision_ids
retrieval_text
quote_text
token_count
continuation_index
chunker_version
embedding_model_id
embedding
content_hash
```

`chunk_id` не является юридической ссылкой. Ответ агента должен ссылаться на `provision_id` и `edition_id`.

### 9.5. Источник

```text
legal_source
------------
source_id
source_url
publisher
downloaded_at
file_name
mime_type
raw_source_hash
storage_path
```

Нужно хранить отдельно:

- hash исходного файла;
- hash очищенного текста;
- hash канонического положения;
- версию правил обработки.

## 10. Статус и период действия

`current`, `future` и `historical` являются состояниями относительно даты запроса, а не вечными свойствами документа.

Основной фильтр:

```sql
valid_from <= :as_of_date
AND (valid_to IS NULL OR :as_of_date < valid_to)
```

Фильтр должен применяться отдельно в каждой ветке retrieval до ранжирования:

- до лексического поиска;
- до векторного поиска;
- до RRF;
- до reranker.

Дополнительные обязательные фильтры:

```text
jurisdiction
review_status = approved
source_scope
tenant/project ACL — для пользовательских документов
```

Текущая раскладка `documents/current`, `future`, `historical` остаётся полезной для ручного контроля, но поисковая логика должна опираться на даты в канонической модели.

## 11. Правила юридического chunking

### 11.1. Основные правила

1. Разные статьи не объединяются в один chunk.
2. Небольшая статья хранится целиком.
3. Большая статья делится только по дочерним положениям.
4. Часть статьи по возможности не разрывается.
5. Пункты и подпункты группируются только внутри общего родителя.
6. Приложения индексируются отдельно от основного текста.
7. Таблицы являются отдельными блоками.
8. Если один пункт превышает лимит модели, он делится по предложениям с сохранением общего `provision_id`.
9. Каждый результат содержит полный путь заголовков.
10. Перекрытие по фиксированному числу символов не применяется между самостоятельными юридическими положениями.

### 11.2. Два текста одного chunk

`retrieval_text` используется для embedding и поиска:

```text
Постановление Правительства РФ № 354
Редакция от 19.12.2025
Правила предоставления коммунальных услуг
Раздел IX
Пункт 98

<текст пункта>
```

`quote_text` содержит только текст нормативного положения, пригодный для точного цитирования.

### 11.3. Соседний контекст

Соседние положения не следует постоянно вклеивать в каждый индексируемый chunk.

После выбора top-кандидата `ContextExpander` может добавить:

- заголовок родительской статьи или раздела;
- предыдущий пункт;
- следующий пункт;
- определение из связанного положения;
- начало таблицы или приложения.

Добавленный контекст маркируется отдельно, чтобы агент не смешивал его с основной цитатой.

## 12. Retrieval pipeline

### 12.1. Общая последовательность

```text
Запрос пользователя
    ↓
QueryNormalizer
    ↓
DateAndJurisdictionResolver
    ↓
обязательный pre-filter
    ├── LexicalRetriever top 50
    └── VectorRetriever top 50
              ↓
         RRF fusion
              ↓
       дедупликация/collapse
              ↓
       external reranker top 20–30
              ↓
       ContextExpander
              ↓
       top 6–10 результатов
              ↓
       CitationBuilder
```

### 12.2. Нормализация запроса

Необходимо выделять и нормализовать:

- номера актов;
- номера статей и пунктов;
- даты;
- типы правоотношений;
- общеупотребительные и юридические варианты терминов;
- сокращения: `ЖК РФ`, `ПП РФ № 354`, `Правила № 491`;
- варианты написания номера: `N 354`, `№354`, `№ 354`.

QueryNormalizer не должен переписывать исходный вопрос без сохранения оригинала.

### 12.3. Лексический поиск

Лексическая ветка нужна для:

- номеров статей и пунктов;
- точных юридических формулировок;
- названий актов;
- редких терминов;
- аббревиатур;
- поиска по реквизитам.

На первом этапе можно использовать PostgreSQL FTS. Это не настоящий BM25, но для текущего объёма подходит как baseline.

Если потребуется строгий BM25, сложные анализаторы, phrase queries и настройка полей, поисковый слой переводится на OpenSearch.

### 12.4. Векторный поиск

Векторная ветка нужна для:

- перефразированных вопросов;
- бытовой формулировки юридической проблемы;
- смыслово близких норм;
- поиска без знания номера акта.

Embedding-модель не определяет юридический статус документа. Все обязательные фильтры задаёт retrieval-service.

### 12.5. Reciprocal Rank Fusion

Базовая формула:

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

Стартовое значение:

```text
k = 60
```

RRF объединяет позиции результатов, а не их несопоставимые raw scores.

Весовые коэффициенты для lexical/vector не следует вводить без evaluation-набора.

### 12.6. Reranking

Reranker получает только кандидатов после RRF, например 20–30 фрагментов.

Он не запускается:

- по всему корпусу;
- при прямом `get_provision`;
- во время обычного metadata lookup.

После reranker остаются 6–10 фрагментов для агента.

### 12.7. Дедупликация

До reranker следует ограничить количество результатов:

- от одной статьи;
- от одного приложения;
- от одной редакции;
- от взаимно перекрывающихся chunks.

Иначе одна длинная статья может вытеснить остальные источники.

## 13. Инструменты агента

Агент не получает SQL, произвольный доступ к БД или возможность самостоятельно конструировать ссылки.

### 13.1. `search_legal`

```text
search_legal(
    query,
    as_of_date,
    jurisdiction,
    status,
    top_k
)
```

Обязанности:

- валидировать параметры;
- вычислить дату применимого права;
- применить pre-filter;
- выполнить lexical и vector retrieval;
- выполнить RRF;
- вызвать reranker;
- расширить контекст;
- вернуть проверяемые citation handles.

Пример результата:

```json
{
  "query_id": "...",
  "as_of_date": "2026-08-27",
  "results": [
    {
      "citation_id": "cit_...",
      "act_id": "ru.gov.pp.354",
      "edition_id": "ru.gov.pp.354@2025-12-19",
      "provision_id": "ru.gov.pp.354@2025-12-19:rules:section-ix:item-98",
      "heading_path": ["Правила", "Раздел IX", "Пункт 98"],
      "valid_at": "2026-08-27",
      "quote": "...",
      "source_url": "..."
    }
  ]
}
```

### 13.2. `get_provision`

```text
get_provision(
    document_id,
    article,
    paragraph,
    as_of_date
)
```

Это точный lookup по каноническому дереву. Embeddings и reranker не применяются.

Инструмент нужен, когда:

- известен акт;
- известна статья или пункт;
- требуется получить полный текст положения;
- требуется проверить соседний пункт;
- нужно выбрать редакцию на дату.

### 13.3. `verify_citations`

```text
verify_citations(
    answer,
    as_of_date
)
```

Детерминированно проверяется:

- существует ли citation handle;
- существует ли положение;
- соответствует ли акт и редакция;
- действовало ли положение на указанную дату;
- содержится ли приведённая цитата в `quote_text`;
- не была ли цитата изменена;
- не относится ли ссылка к будущей или утратившей силу редакции.

Проверка того, логически ли норма подтверждает вывод модели, требует отдельных правил или дополнительного LLM-прохода. Это не следует выдавать за полностью детерминированную проверку.

## 14. Цитирование

Агент должен ссылаться не на текстовое имя статьи, придуманное самостоятельно, а на полученный `citation_id`.

Рекомендуемый внутренний формат ответа модели:

```text
Управляющая организация отвечает за содержание общего имущества [CIT:cit_123].
```

Перед выдачей пользователю backend:

1. извлекает все `[CIT:...]`;
2. проверяет каждый идентификатор;
3. заменяет его на пользовательское представление;
4. добавляет акт, редакцию, положение и ссылку на источник;
5. блокирует или маркирует непроверенные утверждения.

Ответ без найденного нормативного источника должен содержать явное предупреждение или отказ от правового вывода.

## 15. Выбор поискового хранилища

### 15.1. PostgreSQL + pgvector — основной MVP

Преимущества:

- единая транзакционная модель;
- простая связь акта, редакции, положения и chunk;
- понятные SQL-фильтры дат;
- JSONB для дополнительной структуры;
- FTS и векторы в одной базе;
- достаточно для текущих 5220 chunks;
- легко проверить точный результат поиска;
- не нужен отдельный поисковый кластер.

Для текущего объёма допустим точный vector scan без HNSW. Это упрощает корректную предварительную фильтрацию и даёт максимальную полноту.

### 15.2. OpenSearch — путь к расширенному поиску

Переход оправдан, если потребуется:

- настоящий BM25;
- сложная русская морфология;
- разные веса заголовка, текста и реквизитов;
- phrase/proximity search;
- native hybrid query;
- native RRF;
- объяснение ранжирования;
- существенный рост корпуса и нагрузки.

OpenSearch должен оставаться поисковой проекцией. Канонические юридические сущности всё равно хранятся в PostgreSQL.

### 15.3. Qdrant — лёгкая vector-first альтернатива

Преимущества:

- payload filters;
- dense и sparse vectors;
- native RRF;
- multi-stage queries;
- простой отдельный сервис.

Недостаток для данного проекта: lexical search по русским юридическим формулировкам и реквизитам менее естественен, чем в PostgreSQL/OpenSearch.

### 15.4. Haystack

Haystack можно использовать для соединения retrieval-компонентов, но он не должен определять каноническую модель документа.

Допустимые компоненты:

```text
DateResolver
LexicalRetriever
VectorRetriever
RRFJoiner
ExternalReranker
ContextExpander
CitationBuilder
```

На первом этапе обычный Python предпочтительнее из-за прозрачности и меньшего количества абстракций.

## 16. Версионирование и воспроизводимость

Каждая сборка должна фиксировать:

```text
corpus_version
source_manifest_hash
parser_version
cleaner_version
chunker_version
embedding_model_id
embedding_dimensions
search_schema_version
built_at
```

При изменении:

- cleaner — повторить очистку, Legal AST, chunks и индексацию;
- parser — повторить Legal AST, chunks и индексацию;
- chunker — повторить chunks и индексацию;
- embedding-модели — пересчитать все embeddings;
- metadata без изменения текста — обновить фильтры и затронутые индексы;
- исходного файла — пересобрать соответствующую редакцию.

Стабильные идентификаторы должны формироваться детерминированно, чтобы повторная сборка неизменённого источника не создавала новые сущности.

## 17. Контроль качества корпуса

### 17.1. Структурные проверки

- каждый `edition_id` относится к существующему `act_id`;
- каждый `provision_id` уникален;
- у каждого дочернего положения существует parent;
- порядок узлов не содержит циклов;
- каждый chunk относится к существующим provisions;
- нет chunks, объединяющих разные статьи;
- обязательные реквизиты источника заполнены;
- временные интервалы не пересекаются недопустимым образом;
- future/historical не попадают в current search;
- не осталось необъяснённых больших разрывов текста.

### 17.2. Проверка полноты текста

Для каждого источника необходимо сравнивать:

- объём извлечённого текста;
- объём текста Legal AST;
- объём исключённых служебных блоков;
- список нераспознанных элементов;
- страницы без текста;
- таблицы без структуры.

Цель — не просто высокий процент coverage, а объяснимый каждый исключённый диапазон.

### 17.3. Golden tests

Нужен эталонный набор документов разных типов:

1. ЖК РФ;
2. ПП РФ № 354;
3. ПП РФ № 491;
4. СанПиН с таблицами;
5. сложный PDF КонсультантПлюс;
6. документ с приложением;
7. историческая редакция;
8. будущая редакция.

Для каждого фиксируется ожидаемое дерево ключевых разделов и положений.

### 17.4. Retrieval evaluation

Нужно подготовить минимум 30–50 контрольных вопросов:

- точный номер статьи;
- точная цитата;
- бытовая перефразировка;
- вопрос с несколькими релевантными актами;
- вопрос на историческую дату;
- вопрос на будущую дату;
- вопрос, на который в корпусе нет ответа;
- конфликт похожих редакций;
- поиск по таблице или приложению.

Метрики:

```text
Recall@10
MRR
nDCG@10
доля корректных редакций
доля корректных citation handles
доля необоснованных ответов
latency по стадиям
```

Сначала измеряется каждая ветка отдельно:

- lexical;
- vector;
- RRF;
- RRF + reranker;
- RRF + reranker + context expansion.

Весовые коэффициенты и лимиты меняются только по результатам evaluation.

## 18. Безопасность и надёжность

### 18.1. Ограничения агента

Агент не должен:

- писать SQL;
- выбирать произвольные таблицы или коллекции;
- указывать произвольный `edition_id` без проверки;
- придумывать статьи и ссылки;
- считать память источником права;
- скрывать отсутствие источника;
- изменять канонический корпус.

### 18.2. Доверенная граница

Retrieval-service отвечает за:

- проверку параметров;
- ACL;
- выбор corpus scope;
- редакцию на дату;
- фильтры;
- логирование;
- citation handles;
- лимиты результатов;
- таймауты модельных API;
- безопасное поведение при недоступности поиска.

Если retrieval недоступен, агент не должен переходить к ответу «по памяти».

### 18.3. Аудит

Для каждого запроса желательно сохранять:

```text
query_id
original_query
normalized_query
as_of_date
filters
lexical_candidates
vector_candidates
rrf_ranking
reranker_scores
selected_chunks
expanded_context
citations_returned
pipeline_versions
latency
```

Это позволит разбирать ошибочные юридические ответы по стадиям.

## 20. Этапы реализации

### Этап 0. Зафиксировать схемы

Результат:

- Pydantic-модели `LegalAct`, `LegalEdition`, `LegalProvision`, `SearchChunk`, `Citation`;
- правила стабильных идентификаторов;
- manifest format;
- JSON Schema;
- примеры для ПП РФ № 354.

Критерий готовности:

- схемы описывают текущий, исторический и будущий документ;
- положения образуют дерево;
- статус вычисляется на произвольную дату.

### Этап 1. Вертикальный прототип на пяти документах

Документы:

- ЖК РФ;
- ПП РФ № 354;
- ПП РФ № 491;
- один СанПиН;
- один сложный PDF КонсультантПлюс.

Результат:

```text
source → parsed JSON → Legal AST → chunks → validation report
```

Критерий готовности:

- ключевые статьи и пункты распознаны;
- отсутствуют колонтитулы в нормативном тексте;
- таблицы и приложения не потеряны;
- повторная сборка детерминирована.

### Этап 2. PostgreSQL и импорт

Результат:

- миграции;
- repository layer;
- импорт Legal AST;
- вычисление временного статуса;
- трассировка до источника.

Критерий готовности:

- `get_provision` точно возвращает положение на указанную дату;
- неверная или отсутствующая редакция не выбирается автоматически.

### Этап 3. Hybrid retrieval

Результат:

- lexical retriever;
- vector retriever;
- RRF;
- внешний reranker adapter;
- context expansion;
- retrieval log.

Критерий готовности:

- filters применены до обеих веток поиска;
- RRF воспроизводим;
- reranker вызывается только для кандидатов;
- результаты содержат citation handles.

### Этап 4. API инструментов

Результат:

- `search_legal`;
- `get_provision`;
- `verify_citations`;
- OpenAPI schema;
- MCP или function-calling adapter для Agent Runtime.

Критерий готовности:

- агент не имеет прямого доступа к SQL;
- неизвестный citation ID отклоняется;
- непроверенная цитата не выдаётся как подтверждённая.

### Этап 5. Полный корпус

Результат:

- миграция всех текущих 43 индексируемых документов;
- отчёт по каждому источнику;
- список ручных исключений;
- corpus version;
- воспроизводимая команда полной сборки.

Критерий готовности:

- нет необъяснённых пропусков;
- current/historical/future корректно разводятся;
- targeted queries находят известные положения.

### Этап 6. Evaluation и настройка

Результат:

- контрольный набор вопросов;
- baseline-метрики;
- сравнение lexical/vector/RRF/rerank;
- выбранные top-k и RRF-параметры;
- регрессионные тесты.

Критерий готовности:

- новая версия pipeline не принимается при ухудшении обязательных метрик;
- исторические и будущие редакции не загрязняют текущие ответы.

### Этап 7. Интеграция с агентом и продуктом

Результат:

- Agent Runtime вызывает только разрешённые инструменты;
- backend хранит проекты и состояние дел;
- нормативный корпус отделён от пользовательских документов и памяти;
- ответы проходят citation verification.

## 21. Что не следует делать сейчас

- Не импортировать сразу весь корпус в новую систему до прототипа на разных форматах.
- Не выбирать chunk size только по количеству токенов.
- Не использовать LLM как единственный юридический парсер.
- Не смешивать текущие, будущие и исторические редакции в одном поиске с последующей фильтрацией.
- Не использовать имя файла как единственный `document_id`.
- Не ссылаться на `chunk_id` в пользовательском ответе.
- Не добавлять GraphRAG без доказанного улучшения evaluation.
- Не добавлять workflow-конструктор только ради визуальной схемы.
- Не вводить веса RRF без тестового набора.
- Не менять embedding-модель без полной контролируемой переиндексации.
- Не удалять текущий FTS5 до появления проверенной замены.

## 22. Открытые вопросы

Перед реализацией нужно принять решения:

1. Где хранить первичный manifest: YAML в Git, PostgreSQL или оба варианта?
2. Какие источники считать каноническими для каждого типа акта?
3. Нужна ли поддержка нескольких редакций одного положения в одном исходном файле?
4. Как представлять примечания правовой системы и редакционные сноски?
5. Требуется ли хранить фактическое изображение страницы для доказуемости цитаты?
6. Как обрабатывать формулы, схемы и многостраничные таблицы?
7. Нужна ли региональная нормативная база и какая модель `jurisdiction` потребуется?
8. Какой формат citation будет показан конечному пользователю?
9. Должен ли `verify_citations` блокировать весь ответ или только проблемный фрагмент?
10. Как разделять нормативный поиск и поиск по документам дела в Agent Runtime?
11. Когда текущего PostgreSQL FTS станет недостаточно и потребуется OpenSearch?
12. Как будет выполняться обновление источников и обнаружение новых редакций?
13. Кто и в каком интерфейсе утверждает результат структурного разбора?
14. Как долго хранить старые corpus versions и embeddings?

## 23. Рекомендуемый ближайший шаг

Следующая практическая задача — не подключение модели и не создание агента.

Нужно реализовать небольшой read-only прототип компилятора для пяти документов:

```text
Docling extraction
    ↓
cleaned intermediate representation
    ↓
LegalStructureParser
    ↓
Legal AST JSON
    ↓
HTML/Markdown review report
```

На этом этапе не требуется:

- PostgreSQL;
- embeddings;
- reranker;
- Agent Runtime;
- frontend.

Сначала необходимо доказать, что проект способен воспроизводимо построить правильную юридическую структуру. Если Legal AST неверен, более сложный поиск только быстрее найдёт неверно подготовленный материал.

## 25. Рабочий глоссарий

**Нормативный акт (`LegalAct`)** — стабильная сущность закона, кодекса, постановления или иного акта независимо от редакции.

**Редакция (`LegalEdition`)** — состояние нормативного акта с собственным периодом действия и источником.

**Положение (`LegalProvision`)** — юридически адресуемая структурная единица: статья, часть, пункт, подпункт, приложение или таблица.

**Legal AST** — каноническое дерево юридической структуры документа.

**Chunk (`SearchChunk`)** — поисковая проекция одного или нескольких связанных положений. Не является самостоятельным юридическим источником.

**Lexical retrieval** — поиск по терминам, формулировкам, реквизитам и номерам.

**Vector retrieval** — поиск по смысловой близости embedding-представлений.

**RRF** — Reciprocal Rank Fusion, объединение нескольких ранжированных списков по позиции документов.

**Reranker** — модель или сервис, повторно оценивающий небольшую выборку найденных кандидатов.

**Context expansion** — добавление родителя, заголовка или соседнего положения после первичного ранжирования.

**Citation handle** — выданный retrieval-service идентификатор проверяемой ссылки на конкретное положение и редакцию.

**Corpus version** — воспроизводимая версия нормативной базы, включающая источники, схемы, parser/chunker versions и поисковые представления.
