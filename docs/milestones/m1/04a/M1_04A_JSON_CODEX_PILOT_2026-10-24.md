# М1-04А: пилот «официальный JSON против разметки Codex» на синтетическом скане

Дата: 24.10.2026. Статус: **разовый диагностический эксперимент** по просьбе владельца. Это не мера прототипа,
не новая партия пула и не изменение протокола оценки.

## Вопрос

Можно ли брать эталон владельцев М1-04А из официального JSON структуры (как в М1-03А), если документ «отсканировать»?
Попутно: насколько эталон, который размечает Codex, совпадает с независимым официальным эталоном.

## Что сделано

1. **Документ.** Постановление Правительства РФ от 13.08.2006 № 491 (двое утверждённых Правил, приложение с формулами,
   вставные пункты с надстрочными номерами 11¹, 29¹–29⁵, 38¹–38⁵, подпункты е¹, д¹–д³). Редакция IPS `rdk = 21`.
   С `ips.pravo.gov.ru` получены карточка, `documenttext` (HTML) и `document_content` (JSON структуры, 167 узлов).
2. **Скан.** HTML напечатан headless Chrome в PDF A4 (32 страницы). Страницы растеризованы при 200 dpi в оттенках
   серого, слегка повёрнуты (±0,6°), размыты, зашумлены и сжаты в JPEG; из картинок собран PDF без текстового слоя
   (`pdffonts` пуст).
3. **OCR.** dots.mocr (OCR-Lab, `ocr.rotation-retry.local.json`) через `legal_rag.corpus extract`:
   32 страницы, 286 размечаемых областей, 1 Picture и 32 области шума.
4. **JSON-эталон.** Каждый абзац HTML получил владельца `owner-path/2` по самому глубокому узлу JSON, диапазон
   `np…npe` которого (в порядке абзацев документа) его покрывает. Конфликтов вложенности нет. Слова OCR-областей
   выровнены со словами HTML (`difflib`): совпали 9 961 из 10 045 слов. Ни одна область не смешивает двух владельцев.
   Без пары остались 7 областей: 4 — кнопка сайта «Список изменяющих документов» (артефакт печати HTML,
   из оценки исключены), 3 — формулы (в HTML это картинки; владелец — предыдущая область, то есть тот же пункт).
   Итого 282 оцениваемые области. Эталон и вход разметчика захешированы до запуска Codex (`freeze-json-gold.json`).
5. **Разметка Codex.** Одно задание `codex exec -c features.memories=false` по соглашению v2. Codex видел только
   TSV, изображения страниц скана и соглашения. По журналу команд JSON, HTML, исходный PDF и скрипты не открывались.
   Единственное дополнение к соглашению — запись надстрочных номеров как `11^1`.
6. **Сравнение.** Оценщиком `evaluate_ocr_owner_gold.py`: JSON-эталон как эталон, разметка Codex как предсказание.

## Результат

| Мера | Совпало | Доля |
|---|---:|---:|
| Владельцы, строгий вариант (без равенств и с `--single-annex --attached-ordinal`) | 282 из 282 | **100%** |
| Продолжения `+` (из JSON: область начинается с того же абзаца HTML, которым кончилась предыдущая) | 27 из 28 | — |

- Сравнение чувствительно: две подставленные ошибки (`S/I` → `S`, `ж` → `е^2`) дали ровно 2 ошибки.
- Одно расхождение по `+`: подпись «Председатель Правительства… М.Фрадков» OCR разбил на две области. В HTML это
  один абзац; Codex по практике прежних партий подписной блок продолжением не помечает. Это разница соглашений.
- OCR распознал надстрочные номера юникодными знаками (`29¹`, `д²`); один раз потерял индекс в заголовке
  раздела I¹ («## I.»). Codex восстановил его по изображению страницы.
- Соглашения совпали без подгонки: гриф «УТВЕРЖДЕНЫ» и заголовок — у Правил (`S`), подпись — у акта (`A`),
  пометы «(Дополнение пунктом…)» — у самого пункта, а не у его последнего подпункта; приложение к Правилам — `S/AN1`;
  вторые Правила — `S2`.

## Выводы и ограничения

- **Маршрут работает.** HTML+JSON → PDF → «скан» → OCR → проекция JSON на OCR-области даёт эталон владельцев без
  ручной разметки и без конфликтов. На этом документе он совпал с независимой слепой разметкой Codex на 100%.
- **Один документ.** Это пилот, а не мера: ни частоту ошибок Codex, ни переносимость на другие виды актов
  отсюда не вывести.
- **Лёгкий случай для OCR и разметки.** Печать браузера даёт чистую вёрстку: OCR-области почти один к одному
  совпали с абзацами HTML (только 1 область из 286 охватывает два абзаца). В настоящих сканах пула есть печати, бланки,
  таблицы, колонтитулы и разрывы. Именно там у прототипа большинство ошибок (например, приказ №90 в партии 7),
  и этот пилот их не проверяет.
- **Консолидированная редакция, а не оригинал публикации.** В тексте есть редакционные пометы и кнопки сайта,
  которых нет в оригиналах пула.
- **Нотация `^` подсказана заданием.** Формат записи надстрочных номеров разметчику задал экспериментатор, знавший
  формат JSON. На владельцев это не влияет, но это не полностью «слепая» нотация.
- **Расхождения соглашений** (подписи, продолжения, кнопки, формулы-картинки) придётся решать правилами проекции.
  Здесь их было 8 областей из 286.

Следующий осмысленный шаг — 5–10 пар JSON+HTML разных видов (закон со статьями и частями, постановление с таблицей,
приказ с формами) и более жёсткая деградация скана. Тогда частоту расхождений Codex и JSON можно будет мерить.

## Прототип v5 на том же OCR (25.10.2026)

Замороженная копия v5 (`20261024-prototype-v5-freeze/ocr_logical_structure-v5.py`, sha256 `6c590866…`, совпадает
с `code-v5.sha256`) прогнана один раз на OCR пилота; оценка тем же оценщиком против JSON-эталона,
`--single-annex --attached-ordinal`. Для справки так же прогнан v6.1 (`e8d2784c…`): владельцы те же.

| Прогон | Верно | Доля |
|---|---:|---:|
| v5 на OCR пилота | 103 из 282 | **36,5%** |
| v6.1 на OCR пилота | 103 из 282 | 36,5% |
| v5 на копии OCR, где в заголовке 7.1 восстановлено «I¹.» (контрфакт, не мера) | 210 из 282 | 74,5% |

Причины ошибок v5 (179):

- **Каскад от одного заголовка — 107 областей только из-за него.** OCR прочитал «I¹. Требования…» как «## I.».
  Прототип принял повтор «I» за вложенный раздел пункта 9, и разделы II–IV со всем содержимым ушли в `S/I/9/…`.
  Виноваты оба слоя: OCR потерял индекс, а прототип вкладывает повторный римский номер вместо того, чтобы закрыть
  уровень. В контрфакте каскад исчезает (+107), но и правильный «I¹.» прототип разделом не считает: 7 областей
  раздела I¹ остаются в `S/I/9`.
- **Надстрочные номера не распознаются — 70 из 72 ошибок контрфакта.** «29¹.», «38².», «11¹.», «6¹.», «е¹)»,
  «д²)», «а¹)» не открывают новый пункт или подпункт: текст остаётся в предыдущей единице, а подпункты вставного пункта
  вкладываются в чужой подпункт (`S/III/29/б/е/в` вместо `S/III/29^3/в`). OCR при этом прочитал индексы верно
  (юникодные `¹²³⁴⁵`). Это чистая логика дерева, а не дефект OCR.
- **Редакционные пометы после последнего подпункта — 2.** «(Пункт в редакции…)», «(Дополнение приложением…)»
  JSON и Codex относят к пункту или приложению, прототип — к последнему подпункту.
- **Продолжения:** прототип нашёл 21 из 28 продолжений, выведенных из JSON, без лишних. (В выводе оценщика
  `continuation.fp = 21` — артефакт: в JSON-эталоне знаков `+` нет.)

Для сравнения: слепая разметка Codex на том же OCR — 282 из 282.

Вывод: на документе с вставными пунктами v5 проваливается из-за двух пробелов в логике дерева, которых пул
партий 1–7 почти не показывал (надстрочные номера в оригиналах публикаций редки: вставки появляются в
консолидированных редакциях). Это ровно тот класс случаев, который корпус JSON+HTML покрывает дёшево.
Пилот — не мера по протоколу: документ синтетический, выбран не случайно, одна редакция.

Файлы: `prototype-runs/` (`v5.json`, `v6-1.json`, `*-vs-json.json`, `counterfactual-I1/` с исправленной копией
извлечения; исходное OCR не менялось).
