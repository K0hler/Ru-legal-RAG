# М1-04А: как восстановить юридическую структуру документа после OCR

Состояние на 19 октября 2026 года. Краткая справка для человека вне проекта.

## Зачем нужна задача

Мы создаём систему поиска и ответов по российским нормативным документам.
Чтобы ответ сопровождался точной ссылкой, системе нужно понимать, где находится
каждый пункт и к какому документу он относится. Например:

```text
Постановление
├── Пункт 1: утвердить Правила
└── Утверждённые Правила
    ├── Раздел I
    │   └── Пункт 1 → подпункт «а» → абзац
    └── Приложение → таблица
```

М1-04А должна автоматически строить такие связи из распознанных PDF,
сохраняя возможность проверить текст по исходной странице.

## В чём проблема

Наш OCR — dots.mocr — выдаёт JSON: текстовые области, их координаты и типы
(заголовок, текст, таблица, сноска). Это описание расположения текста на страницах.
Юридические связи приходится восстанавливать отдельной программой — парсером.

Один пункт может занимать несколько областей и страниц. Нумерация может
начинаться заново внутри Правил или приложения. Цитата поправки может содержать
собственные пункты. Сноска может продолжаться на следующей странице без номера.
Поэтому начало очередной OCR-области нельзя автоматически считать началом
нового юридического элемента.

Реальный пример: в постановлении №416 страница начинается продолжением
пункта 21 — «утвержденных постановлением…». Наш парсер принимает эти слова
за начало нового утверждённого документа. После этого он не может правильно
разместить пункты 22–23. Текст сохранён, но точных ссылок на эти пункты нет.

Другие существенные ошибки — приложение присоединяется к постановлению вместо
утверждённых Правил; продолжение сноски теряет связь с началом; таблица остаётся
без понятной связи с нормой. Такие ошибки могут изменить смысл будущего ответа.

## Что показали испытания

| Инструмент | Результат наших проверок |
|---|---|
| dots.mocr | Даёт пригодные для дальнейшей обработки текст, координаты и категории. Возможны ошибки распознавания и разметки. |
| Наш основной парсер | Часть структуры восстанавливает; некоторые ошибки границ оставляют без определённого места весь последующий текст. |
| Dedoc | Профиль `foiv_law` справился с проблемными пунктами №416, но на других документах ошибается в связях приложений, сносок и таблиц. |
| Docling | В проверенных прямых JSON-пробах сохранил большую часть данных, но нужную вложенность юридических пунктов не построил. |

Более богатые теги другого OCR, например Marker, сами по себе не доказывают
правильность юридических связей. Для описанной ошибки №416 нужный текст уже
правильно присутствует в JSON. Оснований менять OCR ради её устранения нет.

## Что уже есть и что предстоит

Основной пайплайн обрабатывает PDF целиком, сохраняет исходники и распознанные
данные, строит диагностические деревья. Повторные сборки по сохранённому JSON
воспроизводятся. Это позволяет проверять новые правила без повторного OCR.

Есть отдельный экспериментальный прототип: сначала он соединяет продолжения
в логические абзацы, затем восстанавливает вложенность с учётом всей
последовательности номеров и границ вложенных документов. На ограниченной
разметке результаты хорошие. Прототип пока не подключён к основному
компилятору; точность таблиц, цитаты поправок и другие требования полностью
не проверены.

Дальше нужны общие правила для классов ошибок: продолжения текста, настоящие
грифы утверждения, приложения, цитаты, сноски и таблицы. Исправления под номер
конкретного акта не подходят. Неоднозначность должна оставаться явной.

Задача будет завершена, когда общий механизм заработает в основном пайплайне
и пройдёт проверку на полных документах, которые не использовались для его
настройки. Проверять нужно правильные номера, связи и сохранность содержания.
Косметические отклонения допустимы, если они не искажают смысл и точную ссылку.

**Сейчас М1-04А остаётся открытой. Главная нерешённая часть — надёжное
восстановление юридических связей между уже распознанными фрагментами.**
