# M1-04 dots.mocr implementation plan

> **For agentic workers:** Use superpowers:executing-plans inline. The owner approved the in-chat design and requested implementation on 16 October 2026. Work on main.

**Goal:** Run the retained dots.mocr PDF pipeline, retain its native evidence, normalize it into source-bound extraction records and connect these records to diagnostic corpus compilation.

**Architecture:** OCR-Lab owns rendering/inference in its existing Docker runtime. A small configurable command adapter stages hash-named PDFs and invokes that runtime; the Legal RAG normalizer consumes its saved JSON without importing GPU libraries. A stable extraction contract separates model-specific JSON from document trees and the existing diagnostic legal grammar. Unsupported legal families remain unresolved, with sanitation-rule qualification owned by M1-06.

**Tech stack:** Python standard library and unittest in Legal RAG; the existing pinned dots.mocr/vLLM image and model in OCR-Lab.

**Spec:** Owner-approved PDF -> OCR -> native JSON -> text-extraction/1 -> document/legal structure design in this chat; acceptance in ../../M1_IMPLEMENTATION_PLAN.md, M1-04.

## Review focus

- Missing, failed, duplicate, out-of-order and image-only pages remain accounted for.

- Runtime failure preserves completed peer outputs and records an actionable exception.
- Paths, volatile API metadata and timings never silently alter canonical content identity.
