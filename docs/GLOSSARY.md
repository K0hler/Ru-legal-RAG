# Словарь Legal RAG

**Контекст:** схема проекта по состоянию на 22.09.2026. Термины `LegalAct`, `LegalEdition`, `LegalProvision`, `SearchChunk` и `CitationHandle` описывают **целевую модель**. В существующем индексе LAW_Data они пока не реализованы как отдельные сущности. Подробнее: [атлас](PROJECT_ATLAS.md), [целевой пайплайн](PIPELINE.md), [реестр источников](SOURCES.md).

## Данные и юридическая структура

| Термин | Простое объяснение | Роль в проекте |
|---|---|---|
| **НПА** | Нормативный правовой акт: закон, постановление и другой документ с правовыми нормами. | Исходный правовой материал. |
| **Корпус (`legal_corpus`)** | Набор подлинников актов, их редакций, реквизитов и проверенных текстов. | Единственный контур, из которого можно брать правовое основание. |
| **Manifest** | Реестр каждого файла: источник, хеш, реквизиты, дата действия, статус проверки. | Позволяет понять, откуда взялся текст и должен ли он попасть в индекс. **План.** |
| **Происхождение (`provenance`)** | Цепочка от найденного текста до исходного документа, страницы и официальной публикации. | Нужна для проверки и повторного открытия первоисточника. |
| **Legal AST** | Дерево юридической структуры: акт → раздел → статья → часть → пункт → подпункт → приложение. | Не даёт смешать соседние нормы при поиске. **План.** |
| **LegalStructureParser** | Детерминированный разборщик заголовков и границ норм. | Строит Legal AST из извлечённого текста. **План.** |
| **LegalAct** | Устойчивый идентификатор акта и его реквизиты независимо от редакции. | Отвечает на вопрос «какой это акт?». **План.** |
| **LegalEdition** | Конкретная редакция акта с периодом применимости и источником. | Отвечает на вопрос «какой текст действовал на нужную дату?». **План.** |
| **LegalProvision** | Адресуемое положение акта: статья, часть, пункт, подпункт, приложение или таблица. | Именно на него, вместе с редакцией, должен опираться правовой вывод. **План.** |
| **SearchChunk** | Удобный для поиска фрагмент, привязанный к `LegalProvision` и `LegalEdition`. | Помогает найти норму; сам по себе не считается правовым основанием. **План.** |
| **`current` / `historical` / `future`** | Папки корпуса LAW_Data для текущих, прежних и будущих материалов. | Сборщик сейчас индексирует `current` и `historical`; классификацию по дате требуется проверять. |
| **Материалы дела (`case_documents`)** | Загруженные письма, акты, фото, ответы органов и другие файлы пользователя. | Источник фактов конкретного дела, а не норм права. |
| **Состояние дела (`project_state`)** | События, адресаты, статусы, действия и черновики внутри приложения JKH. | Помогает вести дело; не подтверждает юридическую норму. |
| **Память агента (`agent_memory`)** | Сохранённый контекст предыдущих разговоров. | Помогает продолжать диалог; не является доказательством или источником права. |

## Поиск и ответ

| Термин | Простое объяснение | Роль в проекте |
|---|---|---|
| **RAG** | Ответ с предварительным поиском в документах. | Система сначала ищет подходящие источники, затем готовит ответ по ним. |
| **Retrieval** | Этап отбора подходящих документов или норм. | Должен найти точное положение применимой редакции. |
| **FTS5** | Полнотекстовый поиск SQLite по словам и фразам. | Текущая поисковая основа LAW_Data и отдельного нормативного индекса JKH. |
| **BM25** | Способ ранжировать текстовые совпадения по словам запроса. | В чате JKH применяется к загруженным файлам дела; нормативный поиск устроен отдельно. |
| **Embedding / векторный поиск** | Числовое представление смысла текста и поиск близких формулировок. | Возможное дополнение к поиску по словам после измерения FTS baseline. **План.** |
| **Hybrid retrieval** | Совместное использование лексического и векторного поиска. | Кандидат для улучшения нахождения норм с другой формулировкой. **План.** |
| **RRF** | Метод объединения нескольких ранжированных списков. | Может свести результаты лексического и векторного поиска. **План.** |
| **Reranker** | Дополнительная модель, которая заново упорядочивает уже найденных кандидатов. | Добавляется лишь при измеренной пользе. **План.** |
| **Контекстное раскрытие** | Переход от найденного фрагмента к целой норме и нужным соседним положениям. | Позволяет учесть исключения и перекрёстные ссылки. **План.** |
| **`get_provision`** | Точный запрос нормы по адресу и дате без обычного ранжирования. | Нужен, когда известна статья или пункт. **План.** |
| **CitationHandle** | Выданный сервисом идентификатор нормы, редакции и координат в первоисточнике. | Связывает ответ с проверяемой ссылкой; модель не должна придумывать его. **План.** |
| **Проверка цитаты (`verify_citations`)** | Сверка идентификатора, редакции, даты и буквального текста цитаты. | Ловит неверный адрес источника; отдельно нужна проверка смысла вывода. **План.** |
| **Claim-level audit** | Проверка каждого юридического утверждения против конкретного подтверждающего текста. | Выявляет выводы, которые ссылка на самом деле не поддерживает. **План.** |
| **Корректный отказ** | Ответ без уверенного правового вывода, если применимой нормы нет или важные факты неясны. | Безопасный исход наряду с ответом и уточняющим вопросом. **План.** |

## Качество и доступ

| Термин | Простое объяснение | Роль в проекте |
|---|---|---|
| **Gold set** | Набор вопросов с вручную проверенными правильными нормами, редакциями и случаями без ответа. | Основа сравнения текущего поиска и будущих вариантов. **План.** |
| **Provision recall@k** | Доля вопросов, для которых верная норма попала в первые `k` результатов. | Измеряет, способен ли поиск вообще дать нужное основание. |
| **Edition accuracy** | Доля ответов с правильной редакцией на дату события. | Ловит цитирование подлинной, но неприменимой редакции. |
| **Claim support** | Доля юридических утверждений, действительно подтверждённых процитированным текстом. | Оценивает обоснованность ответа, а не наличие ссылки как таковой. |
| **ACL** | Правила доступа к данным для конкретного пользователя или проекта. | Особенно важны, если из локального JKH получится многопользовательский сервис. **План.** |
| **Вертикальный срез** | Маленькая версия всей цепочки от нескольких исходных актов до проверяемого ответа. | Первый предлагаемый шаг: пять разных НПА, структурный разбор, FTS, точная норма и ссылка. |

## Имена проектов

| Имя | Что это | Статус связи с Legal RAG |
|---|---|---|
| **LAW_Data** | Локальный корпус НПА, извлечение текста и SQLite FTS5. | Существующий отдельный проект; расширенный структурный слой запланирован. |
| **JKH** | Локальное приложение для ведения дел ЖКХ, чата, документов и черновиков жалоб. | Существующий продукт с собственным нормативным поиском и отдельным поиском по файлам дела. |
| **Dify / RAGFlow** | Испытанные платформы для RAG. | Эксперименты и варианты будущей интеграции; не центральный работающий слой этой схемы. |

**Ключевое различие:** `SearchChunk` помогает *найти* текст; `LegalProvision` + `LegalEdition` позволяют *обосновать* вывод на нужную дату. Файл дела сообщает *факт*, но не устанавливает правовую норму.
