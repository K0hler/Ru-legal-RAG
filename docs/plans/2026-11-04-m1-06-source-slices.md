# М1-06: исходные диапазоны в OCR AST

> Исполнение одного интеграционного пункта через
> `superpowers:subagent-driven-development`; независимое ревью и итоговая проверка.

**Цель:** автоматически представить два пункта, попавших в одну область OCR,
с разными владельцами и точными непересекающимися исходными диапазонами.

**Архитектура:** сохранить `text-extraction/1` и native/official маршруты
неизменными; OCR AST получает `legal-ast/3` и `ocr-owner-ast/5`. Срезы относятся
к неизменным `text_node.raw_text`; физические область, страница, категория и bbox
сохраняются. Новая версия не выдаёт повторяемость парсера за независимую приёмку.

**Технологии:** существующий Python, pytest, Ruff; без новых зависимостей.

**Основание:** М1-06/G13 в `M1_IMPLEMENTATION_PLAN.md`, задача3
`2026-11-04-m1-06-sanpin-structure.md`, первый отказ `qualification-01/`.

## Ограничения

- Работа на `main` по указанию владельца. Не менять сохранённые OCR, PDF,
  первые результаты и исходные контроли. Старые `/2` доказательства остаются
  читаемыми и проверяются по прежнему исходному контракту.
- Ни даты, ни номера/названия актов, ни хеши/файлы конкретных актов не управляют
  производственными правилами. Не угадывать геометрию текстового фрагмента.
- Нативный JSON/HTML AST остаётся `/2`; изменение касается OCR.
- `pdf_structure_unqualified`, фактические структурные/исходные неопределённости
  и юридические ограничения сохраняются. Поддержка диапазонов сама не закрывает G13.
- Исходный учёт ведётся по интервалам символов, не по числу упоминаний токена.
  Разные листья могут ссылаться на один токен только непересекающимися срезами.

## Контракт

- Каждый OCR-лист содержит `text_slices`: список
  `{text_node_id, start, end}` с полуинтервалами относительно `raw_text` токена.
  `original_text` точно равен последовательности этих срезов, включая пробелы.
  `source_spans` сужаются на те же границы; source bbox остаётся физическим.
- Для каждого токена длиныL срезы покрывают `[0,L)` без пропусков/пересечений;
  пустой токен имеет ровно один явный `[0,0)`. Таблицы не делятся этим правилом.
- У физической области одна запись `region_bindings`. Если владельцев несколько,
  `disposition=partitioned`, агрегированные owner/address — null, а `fragments`
  содержит упорядоченные start/end/owner_path/address/disposition/continuation.
  Область не превращается в список альтернативных владельцев.
- Диапазоны физической области относятся к исходному OCR-тексту её токенов,
  не к очищенному `view` или новому склеенному абзацу. При необходимости пакет
  исходных контролей явно содержит эту проекцию рядом с неизменным raw OCR.
- Адреса листьев, начинающихся в одном блоке, различаются исходным смещением;
  `node_id` сохраняет связь source SHA/parser version/address.
- Начало новой единицы внутри области имеет точный `anchor_source_spans`.
  Для первого отказа это `[795,833)` токена62, не начало области и не весь токен.
- Учёт `/3` явно указывает интервальную основу и корректно учитывает частично
  parsed/unresolved/excluded токены; сумма исходных символов точна. Старые
  token-count invariants `/2` не применяются к `/3` молча.
- Независимые контроли `/2` вводят `partitioned` область с полным списком
  ожидаемых владельцев диапазонов и точным `start_text_offset/start_text_quote`
  для единицы внутри области. Контроли `/1` продолжают работать для областей
  с одним владельцем. Первая версия контролей сохраняется отдельно.

## Внимание при ревью

- Пропуск/двойной учёт одного символа, особенно на границе двух токенов.
- Якобы точные offsets, полученные из `view`, а не исходных строк.
- Самосогласованные, но неверные владельцы или начало маркера на смещении0.
- Повтор физического region_id, потерявший второго владельца в словаре.
- Успех нового AST при независимом проверяющем коде, который игнорирует срезы.
